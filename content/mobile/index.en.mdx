## Context

<p>
The business wanted to ship this quickly. At the time the work started I was the only designer and was already supporting two other teams, so I didn't have the bandwidth to take it on right away. The developer went ahead and built a first working version from the PM's spec, with the understanding that the design would be reworked once I could focus on it.
</p>

<p>
The PM had written the spec, so the feature scope and business rules were his. My side was the design: how the flows worked, how the screens were structured, and how the app behaved.
</p>


</section>
<section id="alignment">

## Aligning on a build that already existed

<p>
I didn't start from a blank file, so the first job was to understand what had already been built and decide what was worth changing. I went through the spec and the implemented app, then met with the PM and the developer to agree on the goals, the deadline, and which flow problems mattered enough to fix for the release versus which could wait. 
</p>

<p>
Because the developer had built the first version expecting it to be reworked, there was no friction about changing it. We went through the issues together and agreed on the direction before any work started, so the redesign was a joint effort rather than a set of corrections handed down to engineering.
</p>

<p>
I mapped the full app as a set of flows organized by how a rep would actually start: recording on the spot without linking anyone, recording from a specific contact, recording from an existing meeting, and creating a record from the meeting list or a contact profile. Seeing it laid out this way made it easier to agree on what the app needed to cover and what was out of scope for the first release.
</p>

<section id="flow">

## Reworking the core flows

<p>
The biggest change was to let reps record first and link the customer afterward. The earlier approach put contact selection before recording, adding friction at the exact moment a rep needs to capture a conversation. The evidence for this came from the product itself: Digima's existing meeting-log feature went largely unused because logging was too manual, so the redesign attacked friction at the point of capture.
</p>

<p>
The wording shown while recording was a harder problem than it looks. The business decided not to give customers the audio file or the raw transcript, out of concern they would feed it into other tools to generate their own summaries. So the recording screen had to set the right expectation without implying the user would get an audio recording or a transcript back. I worded it around the actual value: the audio is being recorded so the app can produce a summary, not so the user ends up with a file or a transcript.
</p>

<section id="design">

## Designing the unhappy paths

<p>
Recording in the field means a lot can go wrong, so I gave the failure states real attention. There are screens for no connection, not enough storage, and uploads waiting for Wi-Fi, plus empty states and access-denied states. These came straight out of the real constraints in the spec: recordings need to upload when the connection comes back, recording keeps working even when a usage quota is hit, and the data has to survive all of it.
</p>

<p>
Designing these properly protects the moment the whole app exists for: a rep who just recorded an important meeting and cannot afford to lose it. One lost recording would end that rep's trust in the product.
</p>

## Designing within a technical constraint: re-skinning React Native Paper

<p>
The developer wanted to build on React Native Paper so the same UI could serve both the Android and the iOS version of the app from one codebase. That set a real constraint on me: rather than design freely and hand over something that would be expensive to build, I designed within that library and re-skinned its components to Digima's look and feel.
</p>

<p>
The tricky part was doing this without breaking implementation. A re-skin that ignores how the underlying components actually work just moves the problem to the developer. So I worked closely with him throughout, checking that the visual changes I wanted mapped onto what the library could do and adjusting where they didn't. The end result carries the Digima look and feel and stays consistent across iOS and Android. Because the designs mapped onto components the library already provided, the developer didn't have to build custom UI from scratch, which saved development time and helped us hit the release deadline.
</p>

<section id="implementation">

## From design to implementation

<p>
Once the designs were approved I wrote the user stories for the build, reviewed each one, and QA'd the implemented screens against the design and the acceptance criteria, logged per platform since some issues were Android-only. The QA caught three kinds of drift: visual, such as pickers rendering Material's default purple instead of our green; behavioral, such as onboarding repeating on every login instead of showing once; and spec violations, such as the build allowing unlimited meeting attendees when the agreed maximum was two. Catching that last category is the point: design QA covers the agreement, not just the pixels.
</p>

<section id="measurement">

## Measurement

<p>
The app is live, so the next question is whether it does its job. I defined the KPIs, worked with the lead developer to make them measurable, and built a dashboard to track them. Instrumentation shipped recently and the data is only starting to accumulate, so there are no results to report yet.
</p>
<p>
The headline metric is the share of recordings delivered end to end. A recording only creates value if it gets summarized and linked to a contact, so the summary shows up on the CRM timeline where the AI agent can use it. Everything else on the dashboard supports that number. The main supporting metrics are the contact link rate, the summary success rate, a lifecycle funnel showing where recordings get lost, and adoption metrics such as weekly active recorders and retention by cohort.
</p>
<p>
Part of this data already existed in the product database. The rest did not. I mapped the gaps and worked with the lead developer to close them. We added the recording ID to the meetings table so events could be joined to recordings, logged upload attempts on the backend to catch recordings that start uploading and never arrive, added a table recording each status change of a summary, and set up GA4 events in the app for the record button and the contact picker.
</p>
<p>
For the dashboard, I first built an HTML mockup on sample data, using AI as the build tool. Starting with a mockup meant we could debate the metric definitions before anyone invested in real reporting. Spending time defining KPIs was essential. For example, a salesperson who cancels a recording on purpose is not a lost recording, and counting it as one would overstate the failure rate. The production version keeps the same page and swaps the sample data for a JSON file that a scheduled job exports from our Redshift reporting warehouse each night.
</p>

<Images withZoom name={props.images.md["dsahbaord-en"]} />

<p>
Two numbers will get most of my attention once the data comes in. The first is the contact link rate. The core design decision was to let salespersons record first and link the customer afterward, and the link rate shows whether that link actually gets made. The second is usage per salesperson over time, meaning recording frequency and retention by cohort, to see whether recording becomes a habit or fades after the first few meetings.
</p>

</section>

<section id="conclusion">

## Conclusion
<p>
This project came down to shipping a complete mobile experience under a tight deadline by reworking a build that already existed, designing the full set of states rather than just the happy path, and adapting a constrained UI library to the Digima brand without making it harder to build. It is also the project where my involvement started latest, and the clearest lesson was that even a short design review of the spec before the first build would have caught the core flow problem on paper instead of in code.
</p>
