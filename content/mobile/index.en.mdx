## Context

<p>
The business wanted to ship this quickly. At the time the work started I was the only designer and was already supporting two other teams, so I didn't have the bandwidth to take it on right away. The developer went ahead and built a first working version from the PM's spec, with the understanding that the design would be reworked once I could focus on it.
</p>

<p>
The PM wrote the spec, so the feature scope and business rules were his responsibility. My focus was on the design, including how the flows worked, how the screens were structured, and how the app behaved.
</p>


</section>
<section id="alignment">

## Aligning on a build that already existed

<p>
Since I did not start from a blank file, my first task was to understand what had already been built and decide what was worth changing. I went through the spec and the implemented app, then met with the PM and the developer to agree on the goals, the deadline, and which flow problems mattered enough to fix for the release versus which could wait. 
</p>

<p>
Because the developer had built the first version expecting it to be reworked, there was no friction about changing it. We went through the issues together and agreed on the direction before any work started, so the redesign was a joint effort rather than a set of corrections handed down to engineering.
</p>

<p>
I mapped the full app as a set of flows organized by the different possible flows a salesperson could actually start a recording from: 
</p>

<ul>
    <li>Recording from a contact profile</li>
    <li>Recording from an existing meeting</li>
    <li>Recording from the previously pre-created meeting</li>
</ul>

<p>
Seeing it laid out this way made it easier to agree on what the app needed to cover and what was out of scope for the first release.
</p>

## Reworking the core flows

<p>
The biggest change was to let salespersons record first and link the customer afterward. The original flow asked salespersons to select a contact before starting a recording. This was clearly creating a point of friction at the exact moment a salesperson needed to capture a conversation, with the customer standing right there. The clue to that being a potential point of friction came from the existing Digima CRM itself. Digima already had a meeting-log feature, and data showed that our users mostly didn't use it because logging was too manual.
</p>

<p>
The wording shown while recording was a harder problem than it looks. The business decided not to give customers the audio file or the raw transcript, out of concern they would feed it into other tools to generate their own summaries. So the recording screen had to set the right expectation without implying the user would get an audio recording or a transcript back. My solution was to word it around the actual value. "The audio is being recorded so the app can produce a summary that would be used to update the Digima AI agent.", not so the user ends up with a file or a transcript.
</p>

<section id="design">

## Designing the unhappy paths

<p>
For salespersons, recording in the field means a lot can go wrong, so the recording's failure states needed particular attention. There are screens for no connection, not enough storage, and uploads waiting for Wi-Fi, plus empty states and access-denied states. These came straight out of the real constraints in the spec: recordings need to upload when the connection comes back, recording keeps working even when a usage quota was hit, and the data has to survive these failure modes.
</p>

<p>
These states were prioritized based on the costs of failure for the user and the business. Data-loss states were designed first, cosmetic states later, because one lost recording had the potential to really impact the user’s trust in the product.
</p>

## Designing within a technical constraint: re-skinning React Native Paper

<p>
The developer wanted to build on React Native Paper so the same UI could serve both the Android and the iOS version of the app from one codebase. That set a real constraint on me because rather than design freely and hand over something that would be expensive to build, I had to design within that library and re-skin its components to Digima's look and feel.
</p>

<p>
The tricky part was doing this without breaking implementation. A re-skin that ignores how the underlying components actually work just moves the problem to the developer. So I worked closely with him throughout, checking that the visual changes I wanted mapped onto what the library could do and adjusting where they didn't. As a result, I was able to match Digima's look and feel, and keep its design consistent across both platforms. And because designs mapped onto existing components, no custom UI was created from scratch, which saved dev time and helped hit the release deadline.
</p>

<section id="implementation">

## From design to implementation

<p>
Once designs were approved, I wrote the user stories, reviewed each one, then QA'd the implementation against the design. The QA caught three kinds of drift:
</p>

<ul>
    <li>Visual, such as pickers rendering Material's default purple instead of our green</li>
    <li>Behavioral, such as onboarding repeating on every login instead of showing once</li>
    <li>Spec violations, such as the build allowing unlimited meeting attendees when the agreed maximum was two</li>
</ul>

<section id="measurement">

## Measurement

<p>
The app is live, so the next question is whether it does its job. I defined the KPIs, worked with the lead developer to make them measurable, and built a dashboard to track them. Instrumentation shipped recently and the data is only starting to accumulate, so there are no results to report yet.
</p>
<p>
The KPIs I was the most interested in capturing were:
</p>

<ul>
    <li>Percentage of summaries added to a contact timeline vs. recordings started: A recording only creates value if it gets summarized, linked to a contact, and shown on the CRM timeline where the AI agent can use it.</li>
    <li>Average time a recording stays unlinked to a contact. The design hypothesis is that allowing a user to link a recording to a contact after a recording has ended rather than before will help remove friction and maximize the number of recordings users actually do, but for this hypothesis to actually work, users need to actually link contacts to recordings afterward. This KPI is the one verifying that hypothesis.</li>
    <li>Adoption over time (weekly active recorders, retention by cohort). For the feature to succeed, users need to make a habit of recording contact meetings.</li>
    <li>A lifecycle funnel showing where recordings get lost.</li>
</ul>

<p>
Part of this data already existed in the product database. The rest did not. I mapped the gaps and worked with the lead developer to close them. We added the recording ID to the meetings table so events could be joined to recordings, logged upload attempts on the backend to catch recordings that start uploading and never arrive, added a table recording each status change of a summary, and set up GA4 events in the app for the record button and the contact picker.
</p>
<p>
For the dashboard, I first built an HTML mockup on sample data, using AI as the build tool. Starting with a mockup meant we could debate the metric definitions before anyone invested in real reporting, and I could iterate on the way the data was to be presented. The production version keeps the same page and swaps the sample data for a JSON file that a scheduled job exports from our Redshift reporting warehouse each night.
</p>

<section id="conclusion">

## Conclusion
<p>
This project came down to shipping a complete mobile experience under a tight deadline by reworking a build that already existed, designing the full set of states rather than just the happy path, and adapting a constrained UI library to the Digima brand without making it harder to build. It is also the project where my involvement started latest, and the clearest lesson was that even a short design review of the spec before the first build would have caught the core flow problem on paper instead of in code.
</p>
